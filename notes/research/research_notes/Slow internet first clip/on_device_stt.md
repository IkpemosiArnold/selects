# On-device (in-browser) open speech-to-text for Selects Web, and the WebKit/iOS and Android limits that constrain it (as of 22 Oct 2026)

Scope: open STT models that can run in a browser tab with word-level timestamps, for Nigerian-accented English on 3 to 4 GB Android phones (MediaTek Helio) and iPhones. The browser's built-in Web Speech API is out of scope (another researcher). No code was changed. File sizes below come from live Hugging Face API tree listings and the GitHub releases API, queried on 22 Oct 2026, unless another date is given. "Download" means encoder + decoder (the files transformers.js or the runtime actually fetches); tokenizer and config files add about 1 to 4 MB more.

Selects Web today (read from the repo, 22 Oct 2026): `src/browser/models.js` loads `onnx-community/whisper-base.en_timestamped` with `{ wasm: { encoder_model: "fp32", decoder_model_merged: "q8" }, webgpu: { encoder_model: "fp32", decoder_model_merged: "q4" } }` on transformers.js 4.3.1 (bundling onnxruntime-web 1.31.0-dev.20260914) and calls the pipeline with `return_timestamps: "word"` per window (`src/browser/asr.worker.js`). From the listing: fp32 encoder 82.5 MB + q8 merged decoder 53.7 MB = 136.2 MB (the "140 MB"), and fp32 encoder 82.5 MB + q4 merged decoder 123.7 MB = 206.2 MB (the "209 MB"). `render.yaml` sends `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: credentialless`.

## Q1. Comparison: which model is smallest and fastest while still accurate enough, with word timestamps?

### Takeaway
On sizes and published WER alone, the best in-browser candidates are Whisper tiny.en/base.en timestamped exports with an all-q8 set (41 MB and 77 MB, against 136 MB today), Moonshine (tiny q8 28 MB, base q8 63 MB, and the streaming v2 models, which are more accurate per MB), and the sherpa-onnx WASM builds. But only Whisper gets word timestamps out of the box in transformers.js 4.3.1. Moonshine has its own word timestamps (added March 2026) only through its own `@moonshine-ai/moonshine-wasm` runtime. Parakeet, Canary and Kyutai are the most accurate, but their web packages are 210 to 670 MB, and none of them has a published phone-browser benchmark.

Only the Whisper path produces word timestamps: [local file `src/browser/node_modules/@huggingface/transformers/src/pipelines/automatic-speech-recognition.js`, v4.3.1](https://github.com/huggingface/transformers.js/blob/main/packages/transformers/src/pipelines/automatic-speech-recognition.js) (read 22 Oct 2026).

### Inferences
- The cheapest saving needs no model change: switching base.en to q8 for both encoder and decoder cuts the CPU download from 136 MB to 77 MB, and tiny.en q8 is 41 MB. For these timestamped exports, "q4" is larger than "q8" for the decoder (base.en 123.7 vs 53.7 MB), probably because the q4 export quantises only MatMul weights and leaves the large token-embedding matrix in fp32 (51,864 x 512 floats is about 106 MB). So q4 should not be read as "smaller".
- Whether a q8 Whisper encoder costs accuracy on this audio is not established. The repo chose an fp32 encoder, but no reason is recorded in notes/MODELS.md. It should be measured on Selects' own eval clips before switching.
- Moonshine base (63 MB q8) roughly matches Whisper base.en on the 7-set average (10.61 vs 11.10) and is several times faster on desktop, at a smaller download. Moonshine v2 streaming small (8.42) beats whisper small.en (9.24) at about 166 MB. Using Moonshine's word timestamps means adopting `@moonshine-ai/moonshine-wasm` (a separate runtime) instead of transformers.js, or porting its DTW step.
- Parakeet and Canary are not practical first-run downloads on phones over Lagos mobile data: 213 MB at the very least, 661 MB for Parakeet 0.6B.

### Gaps
- No public real-time-factor or peak-RAM measurement in a phone browser (Android Chrome on a MediaTek Helio, or iPhone Safari) for any of these models. Every speed figure above is desktop or server. RAM at runtime: no published numbers except Vosk's "about 300 MB" for small models.
- Open ASR WER for the multilingual whisper tiny/base/small is not in the leaderboard CSV I read (only the .en variants are listed).
- Whether the onnx-community distil-small.en export has the alignment heads and cross-attention outputs that transformers.js word timestamps need was not verified. No `_timestamped` distil repo appeared in searches.

## Q2. Whisper family: onnx-community sizes per quantisation, and do timestamped exports exist for tiny and small?

### Takeaway
Yes. `onnx-community` publishes `_timestamped` exports for tiny, tiny.en, base, base.en, small, small.en and large-v3-turbo, with fp32, fp16, int8/q8 ("quantized", "uint8"), q4, q4f16 and bnb4 files. Their sizes are the same as the non-timestamped exports to within 0.1 MB.

### Cited Findings
- Merged decoder sizes, timestamped exports, in MB (fp32 / fp16 / q8 / q4 / q4f16 / bnb4): tiny(.en) 118.7 / 59.6 / 30.7 / 86.8 / 46.0 / 86.2; base(.en) 208.7 / 104.7 / 53.7 / 123.7 / 68.5 / 122.2; small(.en) 615.7 / 308.5 / 156.8 / 233.4 / 145.8 / 226.3; large-v3-turbo 688.1 / 344.3 / 440.0 / 334.2 / 193.6 / 327.7: [HF tree API, onnx-community `_timestamped` repos](https://huggingface.co/onnx-community/whisper-tiny.en_timestamped/tree/main/onnx) (queried 22 Oct 2026).
- Encoder sizes, in MB (fp32 / fp16 / q8 / q4 / bnb4): tiny 32.9 / 16.5 / 10.1 / 9.0 / 8.6; base 82.5 / 41.3 / 23.2 / 18.8 / 17.6; small 352.8 / 176.5 / 92.2 / 66.2 / 60.9; large-v3-turbo 2,547.9 (external data) / 1,274.4 / 644.9 / 425.0 / 385.7, plus q4f16 370.0: [same listings](https://huggingface.co/onnx-community/whisper-small.en_timestamped/tree/main/onnx).
- The non-timestamped `onnx-community/whisper-tiny.en` and `whisper-small` have nearly identical sizes (for example, tiny.en merged q8 decoder 30.7 MB, small merged q8 decoder 156.8 MB): [whisper-tiny.en](https://huggingface.co/onnx-community/whisper-tiny.en/tree/main/onnx), [whisper-small](https://huggingface.co/onnx-community/whisper-small/tree/main/onnx).
- `onnx-community/whisper-tiny.en_timestamped` had 28,400 downloads (HF API, 22 Oct 2026): [HF model search API](https://huggingface.co/api/models?search=whisper-tiny.en_timestamped).
- The Moonshine v2 paper's desktop latency table (Apple M3) gives Whisper Tiny 289 ms, Whisper Base 553 ms and Whisper Small 1,940 ms response latency, with compute load of 8.46%, 16.19% and 56.84%: [arXiv 2602.12241, Table 2, 12 Feb 2026](https://arxiv.org/html/2602.12241).

### Inferences
- If accuracy on Nigerian English holds up, the smallest timestamped Whisper set is tiny.en at q8 (40.8 MB), and the next is tiny.en with an fp32 encoder and q8 decoder (63.6 MB). base.en at q8 (76.9 MB) is about 56% of today's 136 MB.
- small/small.en (217 to 249 MB at best) is larger than today's model. That is the wrong direction for the "slow internet first clip" problem.

### Gaps
- No published WER comparing q8 and fp32 Whisper encoders in ONNX Runtime Web.

## Q4. Moonshine (tiny/base v1, Moonshine v2 streaming 2026): sizes, ONNX/transformers.js, word timestamps

### Takeaway
Moonshine is the strongest size-to-accuracy option for English. v1 tiny q8 is 28 MB, base q8 is 63 MB, and the v2 streaming tiny/small/medium models are 34M/123M/245M params, MIT-licensed, English-only. transformers.js supports Moonshine v1 but returns no word timestamps. Moonshine's own runtime added cross-attention word timestamps in March 2026 and ships a WASM npm package. Its default WASM build needs cross-origin isolation (require-corp) for threads, and a single-thread build is optional.

### Cited Findings
- Moonshine v2 ("Ergodic Streaming Encoder ASR", Kudlur, King, Wang, Warden) was submitted to arXiv on 12 Feb 2026. Params: Tiny 33.57M, Small 123.36M, Medium 244.93M. WER average across 8 Open-ASR sets: 12.01 / 7.84 / 6.65. LS clean 4.49 / 2.49 / 2.08; LS other 12.09 / 6.78 / 5.00. English only; multilingual is future work. The paper says only "permissive license": [arXiv 2602.12241](https://arxiv.org/html/2602.12241).
- Desktop latency (Apple MacBook M3, NOT phone): Moonshine v1 Tiny 27 ms, v1 Base 44 ms, v2 Tiny 50 ms, v2 Small 148 ms, v2 Medium 258 ms, against Whisper Tiny 289 ms and Base 553 ms. The paper reports no phone, Raspberry Pi or browser numbers: [arXiv 2602.12241, Table 2](https://arxiv.org/html/2602.12241).
- Licence: the moonshine-ai/moonshine README says code is MIT and "The models are MIT by default too, in every language and at every size", except the legacy non-streaming non-English models (Moonshine Community License, non-commercial): [github.com/moonshine-ai/moonshine](https://github.com/moonshine-ai/moonshine) (fetched 22 Oct 2026). The leaderboard lists moonshine tiny/base/streaming as MIT: [CSV f82da85](https://huggingface.co/datasets/hf-audio/open-asr-leaderboard-results/blob/f82da8589575706245e606f6c845bb3df6c93c71/english_short_latest.csv).
- Word timestamps: "Moonshine now supports optional word-level timestamps ... derived from the model's own cross-attention alignment, no external alignment model or second pass required. Works with both non-streaming and streaming models." They need an attention-enabled decoder (`decoder_with_attention.ort` or `decoder_kv_with_attention.ort`), described as "same weights, same size, same speed", and use DTW over cross-attention: [docs/word-level-timestamps.md](https://github.com/moonshine-ai/moonshine/blob/main/docs/word-level-timestamps.md) (first committed 16 Mar 2026). A `WordTiming` type exists in the WASM binding (`language-bindings/wasm/src/types.ts`): [GitHub code search, 22 Oct 2026](https://github.com/moonshine-ai/moonshine/tree/main/language-bindings/wasm).
- Web runtime: `npm install @moonshine-ai/moonshine-wasm` (package.json version 0.1.5). Models are downloaded at runtime and cached in Cache Storage `moonshine-models-v1`. "The default build enables SIMD + multithreading ... which requires cross-origin-isolated" with `Cross-Origin-Embedder-Policy: require-corp`, and a single-thread build is available via `-DMOONSHINE_WASM_SINGLE_THREAD=ON`: [language-bindings/wasm/README.md](https://github.com/moonshine-ai/moonshine/blob/main/language-bindings/wasm/README.md) (fetched 22 Oct 2026). The changelog lists releases 0.1.1 (6 Aug 2026) and 0.1.2 (13 Aug 2026) and "Smaller WebAssembly downloads after ORT-only packaging": [CHANGELOGS.md](https://github.com/moonshine-ai/moonshine/blob/main/CHANGELOGS.md).
- The older npm package `@moonshine-ai/moonshine-js` is at 0.1.29, last modified 3 Jul 2025 (npm registry, 22 Oct 2026).
- transformers.js 4.3.1 includes `MoonshineForConditionalGeneration` and routes `moonshine` to `_call_moonshine` (no word-timestamp path): [local transformers.js 4.3.1 source](https://github.com/huggingface/transformers.js) (read 22 Oct 2026). A WebGPU demo exists: [webml-community/moonshine-web Space](https://huggingface.co/spaces/webml-community/moonshine-web) (145 likes).
- ONNX sizes: see Q1. Official v2 streaming repos ship safetensors only (tiny 176.2 MB, small 560.6 MB): [moonshine-ai/moonshine-streaming-tiny](https://huggingface.co/moonshine-ai/moonshine-streaming-tiny/tree/main), [moonshine-streaming-small](https://huggingface.co/moonshine-ai/moonshine-streaming-small/tree/main). Third-party ONNX: [Masterx/moonshine-streaming-tiny-ONNX](https://huggingface.co/Masterx/moonshine-streaming-tiny-ONNX) (int8 frontend 8.3 + encoder 7.9 + adapter 5.2 + cross_kv 1.3 + decoder_kv 53.6 MB), [Workmind/moonshine-streaming-small-ONNX](https://huggingface.co/Workmind/moonshine-streaming-small-ONNX) (tagged transformers.js).
- A Hugging Face discussion asked whether moonshine-tiny can output word timestamps, with no answer shown: [moonshine-tiny discussion #4](https://huggingface.co/moonshine-ai/moonshine-tiny/discussions/4) (undated in the snippet).

### Inferences
- If Selects moves to Moonshine for word times, it needs the Moonshine WASM runtime (the second runtime alongside ORT-web in transformers.js), or a custom DTW over cross-attention outputs from a re-exported ONNX decoder. On iPhone the multithreaded default build will not get threads under the current COEP credentialless header (see Q10).
- Moonshine v1/v2 handle short segments (the paper targets live, latency-critical speech). Selects already windows audio (`planWindows`), so that fits.

### Gaps
- No Moonshine accuracy figures on African-accented English were found.
- The download size of the official Moonshine WASM model bundle (download.moonshine.ai manifest) was not retrieved.
- Quality of Moonshine's word timestamps against Whisper DTW timestamps: the repo has a `core/word-alignment-benchmark.cpp`, but I did not find published numbers.

## Q5. NVIDIA Parakeet TDT 0.6B v2/v3 and Canary 180M flash / 1B: web ports, sizes, word timestamps

### Takeaway
Web ports exist. parakeet.js (MIT, ONNX Runtime Web, WebGPU encoder + WASM decoder, word timestamps) and istupakov's onnx-asr exports are the main ones. ## Q9. Accuracy on Nigerian / African-accented English

### Takeaway
No source reports WER for Whisper tiny/base or Moonshine on African-accented English. The smallest Whisper with published AfriSpeech numbers is small (0.391 test WER zero-shot; small.en 0.414). Off-the-shelf Whisper large-v3 is about 26.5% WER on Nigerian speakers, and Parakeet v2 is worse (32.6%). Accent-specific fine-tunes help a lot: Intron's commercial Sahara V2 reaches 12.8% on Nigeria, and a community whisper-small fine-tune reaches 20.7% on Hausa/Igbo/Yoruba-accented clips (but under a non-commercial licence). English-only (.en) models did slightly worse than multilingual ones on AfriSpeech.

### Cited Findings
- AfriSpeech-200 (Olatunji et al., arXiv 30 Sep 2023, TACL 2024), pretrained models, test WER general / clinical / both: whisper-large 0.240 / 0.375 / 0.306; whisper-medium 0.276 / 0.392 / 0.332; whisper-medium.en 0.304 / 0.414 / 0.358; whisper-small 0.330 / 0.455 / 0.391; whisper-small.en 0.350 / 0.482 / 0.414; nvidia conformer-ctc-large dev both 0.448; wav2vec2-large-960h 0.717; Azure 0.391; AWS 0.442; GCP 0.578. Fine-tuned whisper-medium-all: test both 0.216. No tiny or base rows: [arXiv 2310.00274v1 Table 4](https://arxiv.org/html/2310.00274v1); also [TACL version](https://direct.mit.edu/tacl/article/doi/10.1162/tacl_a_00627/118796/AfriSpeech-200-Pan-African-Accented-Speech-Dataset).
- Same paper, Nigerian accents test WER (Table 6), "Whisper" (open-source, size not stated in the extract) against fine-tuned Whisper: Yoruba 0.327 to 0.218, Igbo 0.338 to 0.197, Hausa 0.358 to 0.243 (Azure: 0.364 / 0.393 / 0.457): [arXiv 2310.00274v1](https://arxiv.org/html/2310.00274v1). Nigerian accents make up about 67% of AfriSpeech-200 (per search summary of the paper).
- Caveat: the same table lists LibriSpeech test-clean WER of 0.167 for whisper-small/medium/large, far above what Whisper normally scores on that set (leaderboard small.en 3.05%), so the paper's normalisation probably differs. Compare models within the paper only: [arXiv 2310.00274v1](https://arxiv.org/html/2310.00274v1) against [CSV f82da85](https://huggingface.co/datasets/hf-audio/open-asr-leaderboard-results/blob/f82da8589575706245e606f6c845bb3df6c93c71/english_short_latest.csv).
- AfriSpeech-MultiBench (Ashungafac, Sanni, Awobade, Gichamba, Olatunji; arXiv 18 Nov 2025, IJCNLP-AACL 2025), Nigeria WER: Intron-Sahara V2 12.83, Intron-Sahara 15.85, Gemini-2.5 Flash 25.90, Whisper-large-v3 26.53, Distil-Whisper-v3.5 26.69, Canary-Qwen-2.5B 26.82, Voxtral 27.84, Parakeet-tdt-1.1B 28.65, Canary-1B-flash 29.00, Parakeet-tdt-0.6B-v2 32.60, IBM Granite-3.3-2B 33.05, GPT-4o Transcribe 40.03. On AfriSpeech-200 overall: Whisper-large-v3 26.49, Parakeet-0.6B-v2 30.20, Sahara V2 11.83. No tiny, base or small models were evaluated, and latency and timestamps were not measured. The tables have internal inconsistencies (for example, Canary-Qwen labelled "1B" in one column): [arXiv 2511.14255v1](https://arxiv.org/html/2511.14255v1).
- A 2026 EACL paper reports WER rising from about 2.0% (LibriSpeech) to 26 to 38% (AfriSpeech, NCHLT) for strong models such as Whisper large-v3: [ACL Anthology 2026.eacl-long.122](https://aclanthology.org/2026.eacl-long.122.pdf) (search summary; not fetched in full).
- DivineAngel317/whisper-small-nigerian-accented-english (card updated 1 Oct 2026, licence CC-BY-NC-SA-4.0): fine-tuned on 15 h of Hausa/Igbo/Yoruba-accented AfriSpeech-200. On 1,185 unseen-speaker test clips: Whisper Small off-the-shelf 37.7% raw / 33.1% adjusted WER, Whisper Large-v3 27.2% / 22.1%, fine-tuned small 20.7% / 20.7%. By accent and domain (adjusted): Hausa clinical 28.6 / general 10.5; Igbo 22.8 / 18.2; Yoruba 25.4 / 17.5. Self-reported, not peer reviewed: [model card](https://huggingface.co/DivineAngel317/whisper-small-nigerian-accented-english).
- rishabbahal/whisper-small-nigerian-accent (the model Selects desktop uses; card dated 3 Oct 2024, Apache-2.0) reports eval WER 48.81 and loss 1.33 on `babs/nigerian-accented-english` test. That is a different test set, so it cannot be compared directly with the numbers above: [model card](https://huggingface.co/rishabbahal/whisper-small-nigerian-accent).
- intronhealth/afrispeech-whisper-medium-all (Apache-2.0, updated 9 Jul 2024) is an open Whisper-medium fine-tuned on AfriSpeech-200: [model card](https://huggingface.co/intronhealth/afrispeech-whisper-medium-all). Intron's Sahara (v2) is a commercial platform. TechCabal reports 57 languages and "more than 500 African accents", with company-reported gains over Whisper, Gemini and others. I found no open Sahara weights: [TechCabal](https://techcabal.com/fr/?p=182961) (date not shown in the snippet).
- Other Nigerian fine-tunes on HF (unevaluated here): benjaminogbonna/whisper-tiny-for-nigerian-common-languages, AllehellA/whisper-small-nigerian-en, ocansey/whisper-small-nigerian-pidgin, kanyekuthi/AfriSpeech-whisper-tiny: [HF search API](https://huggingface.co/api/models?search=nigerian%20whisper) (22 Oct 2026). microsoft/paza-whisper-large-v3-turbo (MIT, Feb 2026) targets Kenyan languages, not Nigerian English: [model card](https://huggingface.co/microsoft/paza-whisper-large-v3-turbo).

### Inferences
- Extrapolating from AfriSpeech (small 0.391; the gap from medium to small is about 6 points), whisper base and tiny will likely be noticeably worse than 39% WER on clinical-style Nigerian speech. General-domain speech (the Selects use case: talks, interviews) is easier (small 0.330). This is extrapolation, not data.
- Multilingual Whisper beat the .en variants on AfriSpeech at small and medium sizes (0.391 vs 0.414; 0.332 vs 0.358). For Nigerian speakers, whisper base (multilingual, same 77 MB at q8) may be a better default than base.en. This should be tested on Selects' own Nigerian eval clips.
- A small fine-tune (tiny or base) on AfriSpeech-200, exported with `_timestamped`-style cross-attention outputs, is the path most likely to give "small and accurate on Nigerian English". DivineAngel317's result (small: 33.1 to 20.7) shows the size of the gain, but its NC licence rules it out for a commercial product. AfriSpeech-200's own licence was not checked.

### Gaps

## Q10. WebKit / iOS Safari runtime limits in 2026

### Takeaway
On iPhone, every browser is WebKit. WebKit still does not implement `COEP: credentialless` (bug 230550 is NEW, last touched 7 Sep 2026), so under Selects' current headers `crossOriginIsolated` is false on iOS. onnxruntime-web then forces `numThreads = 1`. WASM SIMD (iOS 16.4+) and WebGPU (iOS 26+) are available. The WebContent process is killed by jetsam at about 1.5 GB on most iPhones (2 GB reported on newer ones). Typed-array and WASM memory is capped at 2 GB on iOS, and Memory64 has not shipped. There are open crash reports for transformers.js Whisper on iOS and an ORT-web memory runaway on Safari 26 with the JSEP/WebGPU build.

### Cited Findings
- COEP credentialless: WebKit bug 230550 "Implement COEP:credentialless", created 21 Sep 2021, status NEW, no resolution, last_change_time 2026-09-07. The latest comment (12 Jun 2026) asks "Any progress on this?": [bugs.webkit.org/show_bug.cgi?id=230550](https://bugs.webkit.org/show_bug.cgi?id=230550) (REST API, 22 Oct 2026). WebKit's 2021 position thread: [webkit-dev, June 2021](https://lists.webkit.org/pipermail/webkit-dev/2021-June/031898.html).
- Developer reports agree: "WebKit (Safari, and every browser on iOS) does not support credentialless, so those pages were never isolated", and the fix used was `require-corp` for WebKit, chosen when `window.credentialless` is absent: [swissspidy/sandburg PR #10](https://github.com/swissspidy/sandburg/pull/10) (date not shown). WKWebView on macOS 26.7.1 with COOP same-origin + COEP credentialless reported `crossOriginIsolated === false`: [leehack/llamadart issue #1025](https://github.com/leehack/llamadart/issues/1025). Background: [StackBlitz blog on cross-browser COOP/COEP](https://blog.stackblitz.com/posts/cross-browser-with-coop-coep/) (2022).
- caniuse (raw data fetched 22 Oct 2026): SharedArrayBuffer on iOS Safari from 15.2, note 3 "Requires cross-origin isolation"; WASM SIMD on iOS Safari from 16.4; WASM threads from 14.5; WebGPU on iOS Safari from 26.0 ("y"), with desktop Safari 26 partial ("only enabled by default on macOS 26 Tahoe or later"): [caniuse sharedarraybuffer](https://caniuse.com/sharedarraybuffer), [wasm-simd](https://caniuse.com/wasm-simd), [wasm-threads](https://caniuse.com/wasm-threads), [webgpu](https://caniuse.com/webgpu).
- ORT-web thread fallback, verified in the bundle Selects ships (onnxruntime-web 1.31.0-dev.20260914): `if(typeof self<"u"&&!self.crossOriginIsolated)ee.wasm.numThreads=1`, with a console warning if numThreads was set without isolation: [local `src/browser/node_modules/onnxruntime-web/dist/ort.webgpu.bundle.min.mjs`](https://github.com/microsoft/onnxruntime/tree/main/js/web) (read 22 Oct 2026).
- Hugging Face CDN headers (checked with curl, 22 Oct 2026): `huggingface.co/.../resolve/...` returns 302/307 with `access-control-allow-origin` echoing the request Origin, and the xet CDN target `us.aws.cdn.hf.co` returns 200 with `access-control-allow-origin: *`. No `Cross-Origin-Resource-Policy` header was seen.
- WebGPU in Safari 26: WebKit's Safari 26.0 notes say "WebGPU is now shipping in Safari 26.0 for macOS, iOS, iPadOS, and visionOS" (quoted in [WebKit bug 299237](https://bugs.webkit.org/show_bug.cgi?id=299237), Sep 2025). One user saw `navigator.gpu` undefined on Safari 26 with the flag shown disabled ([same bug](https://bugs.webkit.org/show_bug.cgi?id=299237)). Canvas flicker with WebGPU on iOS 26.0.1 was fixed in trunk ([bug 301627](https://bugs.webkit.org/show_bug.cgi?id=301627), Oct 2025). Safari 26 shipped Sept 2025 (WWDC25 announcement June 2025: [Privacy Guides repost of the WebKit blog](https://discuss.privacyguides.net/t/news-from-wwdc25-webkit-in-safari-26-beta/28226)).
- Memory per tab: a WebKit Bugzilla comment says the WebContent process on most iPhones has an OS-defined limit of 1.5 GB (iPads higher), and that typed arrays and WASM memory sit in a region capped at 2 GB on iOS: [bugs.webkit.org 221530](https://bugs.webkit.org/show_bug.cgi?id=221530) (comment date not captured). An August 2025 WebKit commit is cited as saying the jetsam limit is still 1.5 GB on iOS, and an iPhone 17 Pro logged a 2,048 MB kill: [Nehanth/pooled issue #207](https://github.com/Nehanth/pooled/issues/207). WebKit's MemoryFootprintMonitor enforces a limit matching the per-process WebContent jetsam limit: [WebKit PR #75688](https://github.com/WebKit/WebKit/pull/75688). An older Apple forum thread covers jetsam per-process limits on 4 GB iPhones: [Apple Developer Forums 688973](https://developer.apple.com/forums/thread/688973). A jetsam kill reloads the page with no catchable exception (same sources). These are developer reports, not Apple documentation.
- A WASM `maximum` of 2,048 MB caused Out of Memory on iOS Safari 16.2, and lowering it to 256 MB fixed it: [godotengine/godot #70621](https://github.com/godotengine/godot/issues/70621).
- Memory64: a February 2026 WebKit comment says Memory64 is the only Phase 5 WASM feature WebKit still lacks. Relaxed SIMD was still behind a flag in Safari as of a 2025 review: [WebKit bugs 300537/300538/300539](https://bugs.webkit.org/show_bug.cgi?id=300538), [platform.uno State of WebAssembly 2024/2025](https://platform.uno/blog/state-of-webassembly-2024-2025/).
- Storage: since Safari 17 / iOS 17 (WebKit blog, 10 Aug 2023), a browser app's origin quota is up to 60% of disk and the overall quota up to 80%. Eviction is per origin, least recently used, triggered by quota, storage pressure or ITP inactivity. Covered: localStorage, Cache API, IndexedDB, Service Worker, File System. `navigator.storage.persist()` is supported, with grants decided by heuristics such as Home Screen install: [webkit.org/blog/14403](https://webkit.org/blog/14403/updates-to-storage-policy/). ITP deletes "all of a website's script-writable storage after seven days of Safari use without user interaction on the site" (IndexedDB, LocalStorage, SessionStorage, media keys, Service Worker registrations and cache); Home Screen web apps have their own day counter: [webkit.org/blog/10218, 24 Mar 2020](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/).
- transformers.js on iOS: "onnx-community/whisper-base is crashing in safari", iPad iOS 18.3.2, fp32/q4, wasm; the page reloads repeatedly. Opened and closed as a duplicate of #1242 on 17 Mar 2025, with no maintainer fix: [transformers.js #1241](https://github.com/huggingface/transformers.js/issues/1241). #1242: "v3 crashes on iOS and macOS devices due to increasing memory usage" (workaround: downgrade to 2.15.1): [#1242](https://github.com/huggingface/transformers.js/issues/1242). "[wasm] RangeError: Out of memory" on mobile Safari: [#953](https://github.com/huggingface/transformers.js/issues/953). "[safari] Unexpected restarts": [#973](https://github.com/huggingface/transformers.js/issues/973). One project got Whisper loading on iPhone by running every ONNX model in one worker, so that only one ORT WASM heap exists: [Joe-Solutions/twolay PR #21](https://github.com/Joe-Solutions/twolay/pull/21).
- ONNX Runtime Web on Safari 26: "[Web] Severe CPU and memory issues in Safari/WebKit 26 with JSEP mode" (opened 18 Dec 2025). After inference, WebContent CPU stays at 250 to 400%+ and memory grows from 1 GB to 14 GB+, with iOS crashes. On an iPad with ORT-web 1.29.0, the JSEP and asyncify WebGPU bundles grew to about 5 GB while the plain WASM build stayed stable. The suspected cause is WebKit's OMG JIT compiling huge (asyncify-inflated) WASM functions (`JSC_useOMGJIT=0` fixed it). Workarounds: pin ORT-web 1.20.x, use the non-JSEP WASM build, or disable WebGPU on WebKit. The stale bot closed it on 18 Jul 2026 with no upstream fix, and discussion continued into Sep 2026: [microsoft/onnxruntime #26827](https://github.com/microsoft/onnxruntime/issues/26827).

### Inferences
- On every iPhone, Selects' Whisper currently runs single-threaded on CPU (or on WebGPU, if the device path picks it). The cause is COEP credentialless, not the device. Two options follow. (a) Serve `Cross-Origin-Embedder-Policy: require-corp` to WebKit, choosing it per user-agent or by a client check for `window.credentialless`. The HF model fetches are CORS-mode `fetch()` calls and HF answers with `access-control-allow-origin`, so they should pass require-corp. But every other no-cors cross-origin subresource (images, fonts, iframes) would need CORP headers. (b) Accept single-threaded WASM on iOS and pick a model small enough for that.
- Selects' WebGPU path loads the ORT WebGPU/JSEP bundle. Given ORT #26827, WebGPU (and possibly the JSEP bundle even in WASM mode) on Safari 26 is a crash risk. Forcing the plain WASM bundle on WebKit is the conservative choice.
- Model weights, activations, the ORT heap (and sherpa's 512 MB initial heap, if adopted) plus the page and the video all share the 1.5 to 2 GB WebContent budget. Loading the Gemma judge in the same tab after Whisper would compete for that budget too.
- The 140 MB download over Lagos mobile data likely failed on size and connection stability, not on Safari limits. transformers.js fetches each file whole, and a dropped connection restarts it (inference, not verified in code). Smaller files (tiny.en q8 at 41 MB, Moonshine tiny at 28 MB) cut the failure exposure roughly in proportion. For non-installed sites, the 7-day ITP rule can delete the Cache Storage copy, forcing a re-download.

### Gaps
- No Apple documentation of per-tab memory limits. The figures are developer reports and WebKit comments, and they vary by device and iOS version.
- I could not read MDN's COEP compatibility table (page last modified 4 Sep 2026). The "credentialless unsupported in Safari" conclusion rests on the WebKit bug status and developer reports.
- Whether transformers.js 4.3.1 still crashes with whisper-base on iOS 26/27 is unknown. The reports are against v3.x, and no 2026 confirmation either way was found.

## Q11. Android Chrome runtime: WebGPU on Mali/PowerVR (MediaTek Helio), threads

### Takeaway
Chrome on Android supports COEP credentialless, so Selects gets cross-origin isolation and multithreaded WASM there. WebGPU has been on by default since Chrome 121 (Jan 2024) for Android 12+ with Qualcomm and ARM (Mali) GPUs. MediaTek Helio phones use Mali (some older ones PowerVR), so many qualify on paper. But 2026 reports describe WebGPU on non-Adreno GPUs as buggy or blocklisted in practice. For 3 to 4 GB Helio phones, multithreaded WASM is the dependable path.

### Cited Findings
- "WebGPU is now enabled by default in Chrome 121 on devices running Android 12 and greater powered by Qualcomm and ARM GPUs. Support will gradually expand to encompass a wider range of Android devices, including those running on Android 11": [Chrome for Developers, "What's New in WebGPU (Chrome 121)"](https://developer.chrome.com/blog/new-in-webgpu-121) (last updated 18 Jan 2024).
- PowerVR: Pixel 10 (Tensor G5, PowerVR) WebGPU in Chrome described as new and buggy, so PlayCanvas falls back to WebGL2 there: [playcanvas/engine #8874](https://github.com/playcanvas/engine/issues/8874) (about June 2026). WebGPU on non-Qualcomm GPUs (Mali, Xclipse, PowerVR) described as unresolved in a September 2026 issue: [MaterDev/turnip-kgsl-shim #2](https://github.com/MaterDev/turnip-kgsl-shim/issues/2).
- COEP credentialless shipped in Chrome 96 (2021), which is why Selects chose it: [Intent to Ship: COEP credentialless, blink-dev](https://groups.google.com/a/chromium.org/g/blink-dev/c/Zr9n9_LG7s4/m/4y-b481hBAAJ). caniuse lists SharedArrayBuffer, WASM threads, SIMD and WebGPU as supported on Chrome for Android 156: [caniuse data](https://caniuse.com/webgpu) (22 Oct 2026).
- transformers.js Whisper with WebGPU had a reported memory leak (tensors not disposed after the pipeline, Chrome/Windows): [transformers.js #860](https://github.com/huggingface/transformers.js/issues/860). An older issue said word-level timestamps were not supported under WebGPU at the time: [transformers.js #820](https://github.com/huggingface/transformers.js/issues/820) (search summary, date not captured).

### Inferences
- On a Helio phone with 4 big+little cores, multithreaded WASM with a q8 tiny/base model is the realistic path. WebGPU on Mali may be absent, slow, or blocklisted, and Selects' WebGPU set (206 MB) is larger than its CPU set anyway.
- Selects' `auto` device rule should not prefer WebGPU on Android Mali/PowerVR, or on iOS Safari 26 (see ORT #26827), without a measured benefit.

### Gaps
- No public benchmark of Whisper/Moonshine in Chrome on a MediaTek Helio device (RTF or RAM).
- I found no official Chrome list of Android GPUs currently allowlisted or blocklisted for WebGPU (chromium issue 1497815 was not read).
