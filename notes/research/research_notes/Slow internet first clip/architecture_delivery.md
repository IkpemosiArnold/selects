# Architecture and delivery for the fastest first reviewable clip on slow connections (Selects Web, as of 22 Oct 2026)

Scope: progressive pipeline patterns, cheap pre-ranking, competitor behaviour on slow networks, model-download delivery tricks, CDN reach near Lagos, and whether Cloudflare R2 fits the zero-cost rule. Repo context read (not changed): `README.md`, `notes/MODELS.md`, `render.yaml`, `src/browser/models.js`, `src/browser/cache.js`.

Repo facts this note builds on (from the repo, 22 Oct 2026):
- Whisper base.en for the browser is `onnx-community/whisper-base.en_timestamped`: fp32 encoder 82,451,730 B + q8 decoder 53,712,196 B + 4,247,506 B of other files = about 140 MB (WASM), or the q4 decoder 123,736,279 B = about 209 MB (WebGPU) (`src/browser/models.js`).
- `src/browser/cache.js` downloads each model file with one plain `fetch()` and pipes it into `cache.put()` in Cache Storage. There is no Range request, no resume, and no retry: a dropped connection at 95% restarts from zero.
- The Render static site sits behind Cloudflare (render.yaml comment, measured 21 Oct 2026; confirmed again live below).

**Live measurement conditions (all "live" numbers below):** run from Arnold's Mac in Lagos on 22 Oct 2026 between 16:37 and 16:50 UTC, connection type unknown (probably Wi-Fi on a fixed or MiFi line, not the iPhone's mobile data). The machine was heavily loaded (load average about 357), so CPU-bound numbers (compression) are slow but the ratios are still valid. Single runs, not benchmarks.

## 1. Progressive / streaming pipeline: show the first candidate clips while the rest continues

### Takeaway
The proven pattern is: split audio on silences into roughly 30 s chunks with a few seconds of overlap, transcribe the first minutes first, score candidate windows as soon as their text exists, show a provisional ranked shortlist, and re-rank as later chunks arrive. For Selects, the bigger win on a slow link is order of operations: with Light mode the first useful bytes are about 1.2 MB of Opus audio per 10 minutes instead of 140 MB of whisper, and text-only judging sends kilobytes, so the first clip can be reviewable before any model download finishes.

### Cited Findings
- Whisper processes fixed 30 s windows; the transformers.js ASR pipeline handles long audio by chunking (`chunk_length_s`) with an overlap (`stride_length_s`) and merging the overlapping text, which is the same mechanism a progressive Selects run would use to transcribe minute 0 to 3 before minute 3 to 10. The chunk-with-stride technique is described in Hugging Face's 2022 post on long-file ASR (written for wav2vec2; the transformers pipelines, and transformers.js, apply the same chunk and stride idea to whisper). Source: [HF blog: ASR chunking](https://huggingface.co/blog/asr-chunking)
- whisper_streaming (Macháček, Dabre, Bojar, IJCNLP-AACL 2023 demo) turns whisper into a streaming system with a "local agreement" policy: a transcript prefix is confirmed only when consecutive updates with new audio agree on it. Reported average latency 3.3 s for English on the ESIC European Parliament test set, on an NVIDIA A40 GPU. Source: [arXiv 2307.14743](https://arxiv.org/abs/2307.14743)
- The ufal/whisper_streaming README says that in 2025 WhisperStreaming "is becoming outdated, replaced by SimulStreaming". The project also notes naive fixed windows can split words mid-way, which is why a stability rule (or VAD-aligned cut points) is needed. Source: [ufal/whisper_streaming on GitHub](https://github.com/ufal/whisper_streaming)
- Riverside's "progressive upload" uploads media while recording is still under way, so the file is ready seconds after stopping, and says incremental upload lowers the risk of losing a session if the connection drops. Riverside suggests at least 5 Mbps up and down. Source: [Riverside blog, progressive video uploading](https://riverside.fm/blog/progressive-video-uploading)
- Size arithmetic for Selects' planned Light mode (derived, not measured): Opus at 16 kbps is 2 kB/s, so 10 minutes of speech is about 1.2 MB; whisper WASM is 140 MB, about 117 times more. At 1 Mbit/s, 140 MB takes about 19 minutes; 1.2 MB takes about 10 s. A 10-minute transcript is roughly 1,500 words, about 9 kB of text. (Model sizes from `src/browser/models.js`; bitrate from the brief.)
- Selects already splits judging into a cheap first stage with no model and a model stage that only sees a shortlist (README "the work is split into a cheap first stage with no model and a slow second stage that only sees a shortlist"), and Smart mode falls back to "the preliminary ranking (the first-stage score, no model)". That preliminary score is exactly what a progressive UI can show first. Source: repo `README.md` (lines 183, 285)

### Inferences
- A progressive Selects run could look like: (1) decode audio locally and run VAD; (2) Light mode: send the first 2 to 3 minutes of speech as the first Opus chunk, then the rest in 1 to 2 minute chunks, each cut at a pause with 1 to 2 s overlap; (3) after each chunk returns, extend the transcript, build candidate windows that lie wholly inside confirmed text, and score them with the existing first-stage heuristics; (4) show the top 1 to 3 candidates as "preliminary" with a playable preview (seek the original video, no render) as soon as the first chunk is scored; (5) send the current shortlist text to the judge (Smart mode, kilobytes) in small batches; (6) re-rank when new candidates arrive, but keep an approved or currently-viewed clip pinned so the list does not jump under the user's thumb.
- "Reviewable" does not need a rendered 9:16 file. A preview that plays the source video between the cut points with captions drawn in the page is reviewable at once; the expensive caption burn and encode can wait until the user approves.
- Windows that straddle the end of the transcribed region should not be scored until the next chunk arrives, otherwise the best moment of minute 3 gets cut mid-sentence.
- Phones pause background tabs (README line 201), so progressive delivery also protects against the user leaving: the first clip exists before the tab is likely to be backgrounded.

### Gaps
- No published measurement of how much ranking quality is lost by judging on the first N minutes only versus the whole transcript. Selects' own eval set could measure this (rank correlation of top-3 on prefix vs full).
- I did not verify current transformers.js 4.x default stride values; check the installed version's `pipelines` source.

## 2. Competitors on slow networks

### Takeaway
The big clippers are cloud-first: they ask for the whole video (or a link the server fetches), and none of the help pages found say anything about slow connections, resumable upload, or audio-only upload. Upload-from-link is the common slow-network escape hatch. Descript explicitly refused a "don't upload the original" option. No African-built clipper with slow-network features was found.

### Cited Findings
- OpusClip: a project can be submitted from YouTube, Google Drive, Vimeo, Rumble, Zoom, StreamYard, Facebook, Twitter links or a local file (help centre "Introduction", undated). Source: [OpusClip help: Introduction](https://help.opus.pro/docs/introduction)
- OpusClip editor "Upload media" page (undated): local MP4, MOV, MKV, PNG, JPG; 200 MB and 15 minute limits with error messages; a progress percentage; no mention of resumable upload, slow connections or links. (This page appears to cover adding media inside the editor, not the main long-video import.) Source: [OpusClip help: Upload media](https://help.opus.pro/docs/article/upload-media)
- OpusClip has an iOS app (help centre says it is available on the App Store); the page and the mobile-app marketing page say nothing about background or resumable upload. Source: [OpusClip help: mobile app](https://help.opus.pro/docs/article/does-opusclip-have-a-mobile-app); [OpusClip mobile app page](https://www.opus.pro/mobile-app)
- Vizard: imports from links (YouTube, Google Drive, Vimeo, Dropbox, Loom and others); help centre gives 8 GB max and 6 hours max length on one page, while the API article says 2 hours and 8 GB (conflict); audio-only uploads not supported; minimum 3 minutes to clip; Free plan 300 upload minutes. Source: [Vizard help: illegal file](https://help.vizard.ai/en/articles/8771594-why-does-it-say-illegal-file-when-i-upload); [Vizard help: API](https://help.vizard.ai/en/articles/9422009-how-to-use-vizard-api); [Vizard help: why can't I use AI clipping](https://help.vizard.ai/en/articles/8767578-why-can-t-i-use-ai-clipping); [Vizard blog on upload sources](https://vizard.ai/blog/what-video-formats-platforms-does-vizard-support-upload-sources-use-cases-social-publishing)
- Descript help centre "Why is my import or upload taking so long?": time depends on upload speed, file size and background processing; recommends a speed test and at least 10 Mbps upload; first troubleshooting step is "check your internet connection". Source: [Descript help](https://help.descript.com/hc/en-us/articles/34610427613325-Why-Is-My-Import-or-Upload-Taking-So-Long)
- Descript feature request "Option to not upload original file to the cloud" (opened 13 Nov 2019) was closed by staff on 12 Dec 2025: "We've since moved to full cloud-based file storage so this is not something that will be considered any time soon." Users in the thread complain about bandwidth and travel use. Source: [Descript feedback board](https://feedback.descript.com/feature-requests/p/option-to-not-upload-original-file-to-the-cloud)
- Descript status incident (27 Jul 2026, resolved): uploads to the media library root failed; workaround was to upload into a folder. Source: [Descript incident mirror](https://isdown.app/status/descript/incidents/629481-issue-with-uploads-to-media-library)
- Riverside records locally on each participant's device and uploads progressively during recording; Magic Clips then finds highlights. Plan access for Magic Clips conflicts between Riverside's page (free plan available) and a third-party guide (Pro). Source: [Riverside progressive upload](https://riverside.fm/blog/progressive-video-uploading); [Riverside clips page](https://riverside.fm/clips); [Ruzuku guide](https://www.ruzuku.com/learn/tools/riverside/record-course-videos)
- Submagic: paste a YouTube link or upload a video; Magic Clips cuts Shorts automatically. Source-length caps by plan (2, 5, 30 minutes) are only reported by a competitor (Choppity) and are unverified. Source: [Submagic YouTube Shorts scheduler](https://www.submagic.co/youtube-shorts-scheduler); [Choppity comparison](https://www.choppity.com/alternatives/submagic/)
- Klap and CapCut "long video to shorts": no official help page on upload limits or slow networks was found in this pass.

### Inferences
- Selects' on-device and Light-mode design is a genuine differentiator for Lagos mobile data: competitors move the whole video (hundreds of MB to GB) up, or require a link to something already uploaded. Selects can move about 1 to 2 MB of speech audio and about 10 kB of text.
- Upload-from-link is worth copying only where it costs nothing: a public YouTube link means the video is already online, but fetching it server-side needs a server with bandwidth and runs into YouTube's terms; this is not zero-cost-safe without more research.
- The competitor gap to exploit in copy: "works on a slow connection, nothing big is uploaded".

### Gaps
- Klap, CapCut and Submagic official help pages with dated slow-network guidance were not found. Opus Clip help pages carry no dates.
- No African-built AI clipper with documented slow-network features was found (searched only briefly).
- Whether OpusClip's iOS app uses iOS background URLSession uploads is unknown.

## 3. Cheap speculative ranking before the AI judge

### Takeaway
A text and audio heuristic stage (sentence completeness, hook phrases, question/answer shape, numbers, laughter or loudness peaks) can rank candidates in milliseconds and needs no download, so it can drive the first preliminary clip. Published highlight-detection work supports adding transcripts to visual cues, but nothing found replaces an LLM judge for "is this a good standalone short". Text-only judging is tiny on the wire.

### Cited Findings
- "Unsupervised Transcript-assisted Video Summarization and Highlight Detection" (arXiv May 2025): fuses video frames and transcripts, trained with reinforcement learning whose reward favours diverse, representative segments with meaningful transcript content; claims transcripts improve over visual-only. The abstract gives no numbers or datasets. Source: [arXiv 2505.23268](https://arxiv.org/abs/2505.23268)
- Open-source clippers use the same two-stage shape: faster-whisper for timestamped transcripts, then an LLM ranks moments on hooks, emotional peaks and quotable lines. Source: [short-video-generator-AI summary](https://www.sourcepulse.org/projects/32873366)
- Sieve's write-up on finding highlights in long-form podcasts describes a transcript-plus-LLM approach for long-form content. Source: [Sieve blog](https://sievedata.com/blog/generate-video-highlights-long-form-content-podcasts)
- Selects already has a first stage with no model that pre-scores windows and passes the top `--judge-n` (default 8) to the judge (README options table, line 423); on a dual-core CPU, scoring one 100-word window with Gemma 3 4B took about a minute while picking from a whole 2,957-word transcript did not finish in 30 minutes (README line 285).

### Inferences
- Useful zero-download signals for the preliminary rank: window starts at a sentence start and ends at sentence end (punctuation or a pause over about 0.6 s); a hook in the first 3 s (a question, "the secret", "nobody tells you", a number, a strong claim); a self-contained answer after a question; speech rate and loudness peaks from the decoded audio (RMS, already available after decode); laughter or applause (energy bursts without words in whisper's output). These cost nothing in bandwidth.
- Judge payload: 8 windows of about 100 words is about 800 words, roughly 5 kB of text, so Smart mode works even on 2G-class links. The judge is not the bandwidth bottleneck; whisper is.

### Gaps
- No published, open, transcript-only highlight detector with measured agreement against human short-form picks was found in this pass.

## 4. Model download tricks (Range resume, compression, sharding, storage, browser APIs)

### Takeaway
Hugging Face's CDN supports HTTP Range with 206 responses and allows the Range header cross-origin (verified live), so resumable, chunked downloads with per-chunk retry are possible today without re-hosting. Responses are not compressed. Quantized and fp16 weights compress poorly (about 0.6 to 0.9), but the fp32 whisper encoder compressed to about 0.54 in two live slices, so a smaller file choice or a compressed self-hosted copy could save about 35 to 40 MB on the WASM set; resume is still the first fix. Background Fetch and the Network Information API exist only in Chromium (not on the iPhone that failed), and Safari's storage can be evicted, so persistence must be requested and the UI must cope with a lost cache.

### Cited Findings
- **Live (22 Oct 2026, Lagos Mac):** `HEAD https://huggingface.co/onnx-community/whisper-base.en_timestamped/resolve/main/onnx/decoder_model_merged_quantized.onnx` returned `302`, `accept-ranges: bytes`, `x-linked-size: 53712196`, `x-xet-hash: aeb01eb3…`, `x-cache: Miss from cloudfront`, `x-amz-cf-pop: LOS50-P5`, and a redirect to `https://us.aws.cdn.hf.co/xet-bridge-us/<repo-id>/<xet-hash>?<signed query>`. The old `cas-bridge.xethub.hf.co` hostname was not used.
- **Live:** the redirected file host answered a `Range: bytes=0-99` GET with `206`, `content-range: bytes 0-99/53712196`, `accept-ranges: bytes`, `access-control-allow-origin: *`, `access-control-expose-headers: *`, `etag` = the xet hash, and `x-hf-cdn-pop: aws-eu-west-3` (AWS Paris). A mid-file range (`50000000-50099999`, following the redirect) also returned 206 with exactly 100,000 bytes.
- **Live:** CORS preflight with `Access-Control-Request-Headers: range` from origin `https://selects.ikpemosi.work` returned `200` on both hosts: huggingface.co replied `access-control-allow-headers: range`, `access-control-max-age: 86400`, and exposes `Accept-Ranges, Content-Range, X-Linked-Size, X-Xet-Hash`; the xet bridge replied `allow-headers: *`, `allow-methods: *`, `allow-origin: *`.
- An earlier report (GitHub issue on HF datasets) said the redirected `cas-bridge.xethub.hf.co` host failed CORS preflight for browser Range reads; a HF forum post says a 16 Jul 2026 docs update dropped `cas-bridge.*` as a legacy endpoint. The live test above shows the current host passes preflight, so that old failure no longer applies to the path Selects uses. Source: [huggingface/datasets issue 7931](https://github.com/huggingface/datasets/issues/7931); [HF forum: CORS and Range](https://discuss.huggingface.co/t/cors-support-for-http-range-requests-on-dataset-files/172172); [HF forum: Download via Xet](https://discuss.huggingface.co/t/download-via-xet/178100)
- HF docs: the Hub stores large files in Xet (chunk-level deduplication) with legacy clients getting a single URL from a bridge that reconstructs the file. Source: [HF Hub docs: Xet](https://huggingface.co/docs/hub/xet); [Xet protocol spec](https://huggingface.co/docs/xet/index.md)
- **Live:** a GET with `Accept-Encoding: gzip, br, zstd` to the xet bridge came back with no `content-encoding` header (bytes are sent raw).
- Tree API (live) lists the sizes Selects could choose from in this repo: `encoder_model.onnx` 82.5 MB (fp32), `encoder_model_fp16` 41.3 MB, `encoder_model_int8`/`quantized` 23.2 MB, `encoder_model_q4` 18.8 MB, `encoder_model_bnb4` 17.6 MB; `decoder_model_merged_quantized` 53.7 MB, `_q4f16` 68.5 MB, `_q4` 123.7 MB. Every file is Xet-backed. Source: [HF tree API for the repo](https://huggingface.co/api/models/onnx-community/whisper-base.en_timestamped/tree/main/onnx)
- **Live compressibility (ratios = compressed / original; lower is better; 5 MB slices except Silero):**
  - Silero VAD fp32 ONNX, whole file 2,243,022 B: gzip -9 0.864, brotli -q11 0.792, zstd -19 0.807.
  - Whisper base.en encoder fp32, bytes 10 to 15 MB: gzip 0.597, brotli 0.484, zstd 0.544.
  - Whisper base.en decoder merged fp16, bytes 10 to 15 MB: gzip 0.910, brotli 0.862, zstd 0.907.
  - Whisper base.en decoder merged q8 (`_quantized`, the file Selects uses), bytes 10 to 15 MB: gzip 0.494, brotli -q9 0.486, zstd 0.439.
  - Whisper base.en encoder fp32, a second slice, bytes 60 to 65 MB: gzip 0.585, brotli -q9 0.536, zstd 0.537 (so the fp32 encoder result held in two places).
  - Whisper base.en encoder q4, bytes 5 to 10 MB: gzip 0.720, brotli -q9 0.627, zstd 0.629.
  - Caution: these are 5 MB slices, not whole files, run once. The fp32 encoder compressing to about 0.54 is far better than the about 0.83 (17% saving) published for typical FP32 models, while the fp16 decoder (0.86 to 0.91) matches the published picture. The likely reason (my inference, not verified): OpenAI released whisper weights in fp16, so an fp32 export is an upcast whose low 13 mantissa bits are zero. If so, the fp16 file carries the same information in half the bytes. The q8 decoder slice (0.44 to 0.49) may be dominated by an unquantized, upcast embedding table; a full-file test is needed before relying on it.
- Published ratios: ZipNN (IBM, arXiv 2411.05239) reports about 17% saving on FP32 models (exponent bytes are the compressible part) and about 33% on BF16, with zstd somewhat behind; gzip/zlib ratios similar to zstd but slower. Source: [IBM Research blog on ZipNN](https://research.ibm.com/blog/Zip-NN-AI-compression); [ZipNN paper](https://arxiv.org/pdf/2411.05239v1)
- A self-reported project (z4ai) says a trained float's mantissa is near random, capping lossless compression at about 1.2x for fp32 and about 1.5x for bf16, with large gains only when quantized values are stored inside a wider float container. Source: [z4ai on PyPI](https://pypi.org/project/z4ai/)
- Background Fetch API: experimental, "limited availability", not Baseline; the browser does the fetch itself so it continues after the page closes, shows progress UI the user can cancel, pauses when offline and resumes on reconnect (MDN, last modified 12 Sep 2026). MDN's table did not render in the fetch; general knowledge is Chromium only (Chrome, Edge, including Android), not Safari or Firefox. Source: [MDN Background Fetch API](https://developer.mozilla.org/en-US/docs/Web/API/Background_Fetch_API)
- Network Information API `effectiveType`: values `slow-2g`, `2g`, `3g`, `4g`, derived from recently observed round-trip time and downlink; "limited availability", not Baseline (MDN, last modified 1 Apr 2024). Historically not implemented by Safari or Firefox (MDN table not captured; verify on caniuse). Source: [MDN effectiveType](https://developer.mozilla.org/en-US/docs/Web/API/NetworkInformation/effectiveType)
- Storage persistence in WebKit (Safari 17 storage policy update): `navigator.storage.persist()` is granted by heuristics such as whether the site runs as a Home Screen web app; a persistent origin is exempt from eviction; browser-app quota is up to 80% of disk overall per WebKit (MDN says about 60% per origin, a conflict). Home Screen web apps keep the same quotas as Safari. Source: [WebKit: Updates to Storage Policy](https://webkit.org/?p=14403); [MDN storage quotas and eviction](https://developer.mozilla.org/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- Safari's 7-day cap on script-writable storage: John Wilander (WebKit) clarified in 2020 that Home Screen web apps are not part of Safari and have their own counter of days of use, which matches actual use of the app. A 2022 WebKit bug reported Home Screen data deleted after 7 days, so behaviour has varied by version. Source: [OSNews on the WebKit clarification](https://www.osnews.com/?p=131566); [WebKit bug 237350](https://bugs.webkit.org/show_bug.cgi?id=237350); [Apple developer forum thread](https://developer.apple.com/forums/thread/710157)
- MDN: Safari and most Chromium browsers approve or deny `persist()` automatically from interaction history, without a prompt. Source: [MDN storage quotas and eviction](https://developer.mozilla.org/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

### Inferences
- **Fix the iPhone failure first with resume, not a new CDN.** Replace the single `fetch()` in `cache.js` with a loop of `Range` requests of 4 to 8 MB each (HF returns 206 and allows the header cross-origin, verified). Store each piece as its own entry (Cache Storage key like `url#part=3`, or an OPFS file written at an offset), retry each piece with backoff, and on the next visit skip pieces already stored. A drop at 95% then costs one piece, not 140 MB. Verify integrity with the `x-linked-size` total and, where feasible, the xet hash or a SHA-256 kept in `models.js`.
- Range requests against the `huggingface.co/.../resolve/` URL follow a 302 each time; better to resolve once, then reuse the signed `us.aws.cdn.hf.co` URL for all pieces until it expires (signed query; refresh on 403).
- Cache Storage needs a whole `Response` per entry, so per-piece entries plus a reassembly step (or a custom loader that feeds pieces to ONNX Runtime as one `Uint8Array`) are needed; transformers.js expects one cached response per file, so Selects would assemble the pieces and then `cache.put()` the full file for transformers.js to find. OPFS supports writing at offsets (sync access handles in a worker), which suits resume without reassembly, but browser support details on iOS Safari should be checked before relying on it.
- **Choose smaller files where accuracy allows:** the encoder in q4 or int8 (18.8 or 23.2 MB) instead of fp32 (82.5 MB) would cut the WASM set from about 140 MB to about 80 MB, but `models.js` notes quantising whisper's encoder costs accuracy; that trade-off needs Selects' own WER check before it ships, perhaps only for a "slow connection" profile.
- Compression is a real but secondary lever. HF sends raw bytes, so any saving needs either (a) picking an already-smaller file, or (b) a self-hosted compressed copy. For the fp32 encoder, measured slices compress to about 0.54 (zstd/brotli) or 0.59 (gzip), so 82.5 MB could travel as roughly 45 to 49 MB. Gzip shards can be inflated in the page with the built-in `DecompressionStream("gzip")`, no library needed; brotli or zstd would need a WASM decoder (support for other formats in `DecompressionStream` not checked). Simpler still: if the fp16 encoder (41.3 MB) is an exact cast of the original fp16 weights, it saves the same bytes with no accuracy change, but it would have to run on WASM (fp16 kernels on the CPU path need checking) or be upcast to fp32 in the page before the session is created.
- Background Fetch is a Chrome-Android-only bonus (useful for the 2 GB Gemma 4 judge on Android). It does nothing for iPhone. Network Information is also Chromium-only: use it to warn and to defer big downloads to Wi-Fi where present, and fall back to a measured throughput probe (time a 1 MB range from HF) elsewhere.
- On iPhone, ask `navigator.storage.persist()` after the first successful download, encourage "Add to Home Screen" for repeat users, and always handle "the model is gone" (Safari eviction) gracefully, with Light mode as the default path that never needs the model.

### Gaps
- Exact iOS Safari support for OPFS `createSyncAccessHandle` / `createWritable` at the current iOS version was not verified in this pass.
- Exact `effectiveType` and Background Fetch support tables were not captured (MDN tables did not render); confirm on caniuse before coding a branch.
- Lifetime of the signed `us.aws.cdn.hf.co` URL was not measured.

## 5. CDN points of presence near Lagos (live tests and docs)

### Takeaway
From this Lagos connection, Cloudflare serves from Lagos itself (LOS colo, about 15 ms RTT), which covers the Selects site because Render sits behind Cloudflare. Hugging Face's front door hits a CloudFront Lagos edge (LOS50) but that only serves the redirect; the model bytes come from AWS Paris (eu-west-3), with about 0.9 s to first byte. jsDelivr was served via Cloudflare Paris for the test file; GitHub release assets via Fastly London. All delivered 1.2 to 3.8 MB/s on this link, so on a good connection the host is not the bottleneck; on mobile data the lack of resume is.

### Cited Findings
- **Live, (a) Hugging Face** `-r 0-4999999` on `decoder_model_merged_quantized.onnx` (following the redirect): `206`, TTFB 0.93 s, 5,000,000 B in 2.24 s, about 2.24 MB/s (first run, 16:38 UTC); second run 16:46 UTC: `206`, TTFB 0.91 s, 4.19 s, about 1.19 MB/s. Front door headers: `x-amz-cf-pop: LOS50-P5`, `via: … cloudfront.net (CloudFront)`, `x-cache: Miss from cloudfront`. Byte host: `x-hf-cdn-pop: aws-eu-west-3` on both fetches.
- **Live, (b) jsDelivr** `https://cdn.jsdelivr.net/npm/onnxruntime-web@1.20.1/dist/ort-wasm-simd-threaded.wasm`: HEAD showed `server: cloudflare`, `cf-ray: …-CDG` (Paris), `x-served-by: cache-fra-…-FRA, cache-bgy-…-BGY` (Fastly Frankfurt and Bergamo behind it), `x-cache: HIT, HIT`. A `-r 0-4999999` request returned `206` with TTFB 0.11 s but delivered 11,246,032 B (more than the requested range; looks like the whole file was sent despite the 206) at about 3.77 MB/s. Treat jsDelivr Range behaviour as unreliable until rechecked.
- **Live, (c) Cloudflare speed test** `speed.cloudflare.com/__down`: `CF-RAY: …-LOS` (Lagos), server-timing `rtt=15410` µs (about 15 ms), 5,000,000 B with TTFB 0.15 s, 2.06 s total, about 2.43 MB/s.
- **Live, (d) selects.ikpemosi.work/**: `HTTP/2 200`, `server: cloudflare`, `cf-ray: …-LOS`, `rndr-id` header (Render), `cf-cache-status: EXPIRED`, `cache-control: public, max-age=0, s-maxage=300`, COOP `same-origin`, COEP `credentialless`; HTML TTFB 0.22 s. The JS bundle `/assets/index-BWgUJiE6.js` came back `content-encoding: br`, `cache-control: public, max-age=31536000, immutable`, `cf-ray: …-LOS`.
- **Live, GitHub release asset** (sherpa-onnx punctuation tarball): 302 from github.com to `release-assets.githubusercontent.com`, served by `Windows-Azure-Blob` through Fastly (`x-served-by: cache-iad-…-IAD, cache-lhr-…-LHR`, London edge), `accept-ranges: bytes`.
- Cloudflare opened a Lagos data centre (its 155th), peering with IXPN and WAF-IX Lagos, so Nigerian traffic is served locally instead of from London or Lisbon (press coverage; date not shown in the result). Source: [PPC Land](https://ppc.land/cloudflare-opens-a-new-data-center-in-lagos/); [Business Wire, 13 Sep 2021 network expansion](https://www.businesswire.com/news/home/20210913005228/en)
- Render docs say static sites are served "over a blazing-fast, reliable, and secure global CDN" without naming it; static sites count against monthly included outbound bandwidth. Source: [Render docs: static sites](https://render.com/docs/static-sites)
- jsDelivr is a multi-CDN (sponsors' networks, load-balanced); a third-party IP listing shows Gcore PoPs in Johannesburg and Cape Town and Cloudflare, Fastly, Bunny among providers; no Lagos PoP evidence found. Source: [jsDelivr about](https://www.jsdelivr.com/about); [Netify jsDelivr profile](https://www.netify.ai/resources/applications/jsdelivr)

### Inferences
- The site itself is already as close to Lagos as it can get for free (Cloudflare LOS via Render). Model bytes travel from Paris; that adds about 0.8 s of first-byte latency per request (TTFB 0.9 s vs 0.15 s from Cloudflare), which matters for many small Range requests: use 4 to 8 MB pieces, not 256 kB, and keep 2 to 3 in flight.
- jsDelivr is not closer than Hugging Face for this route (Paris edge), and its Range handling looked odd, so it is not a better model host.
- These numbers come from a fixed-line-like connection; an iPhone on Lagos mobile data will see lower throughput and more drops, which again points to resume rather than PoP choice.

### Gaps
- No live test from Lagos mobile data (MTN, Airtel, Glo) was possible from here; results may differ by carrier and peering (CloudFront and Cloudflare both have Lagos edges, but HF's byte host does not).
- Whether HF's `us.aws.cdn.hf.co` would ever serve from a CloudFront Lagos edge (cached) was not observed; both fetches said `aws-eu-west-3`.

## 6. Cloudflare R2 (or other free mirrors) nearer Lagos, under the no-card rule

### Takeaway
R2 fails the hard rule: Cloudflare's own get-started page says an R2 subscription via checkout is required, and third-party guides say activation needs a card or PayPal. Cloudflare Pages (or Workers static assets) can serve 5 to 20 MB shards from the Lagos edge for free with no card, because the per-file cap is 25 MiB, which fits a sharded model.

### Cited Findings
- R2 pricing (last updated 1 Oct 2026): free tier per month is 10 GB-month storage (Standard class only), 1 million Class A and 10 million Class B operations, egress free; usage above the allowance is billed at standard rates. The page says nothing about payment methods. Source: [Cloudflare R2 pricing](https://developers.cloudflare.com/r2/pricing/)
- R2 get started (last updated 21 Apr 2026): "You need a Cloudflare account with an R2 subscription" and "Complete the checkout flow to add an R2 subscription to your account." Source: [Cloudflare R2 get started](https://developers.cloudflare.com/r2/get-started/)
- Third-party reports say enabling R2 asks for a payment method (card or PayPal), described as verification; a forum post mirroring a Cloudflare status update (Sep 2025) said users without a payment method on the account could not add one while enabling R2 and should add a payment method first. Source: [eastondev blog, 30 Nov 2025](https://eastondev.com/blog/en/posts/dev/20251130-r2-picgo-setup/); [Cloudflare billing: create billing profile](https://developers.cloudflare.com/billing/create-billing-profile/); [Centmin Mod community thread](https://community.centminmod.com/threads/cloudflare-queues-delivery-latency.29331/next)
- Cloudflare billing policy: for usage-based services Cloudflare may preauthorise the card; for R2, a failed payment means buckets return errors. Source: [Cloudflare billing policy](https://developers.cloudflare.com/billing/understand/billing-policy/index.md)
- Cloudflare Pages limits (last updated 5 Sep 2026): up to 20,000 files on the Free plan; maximum single asset 25 MiB. Source: [Cloudflare Pages limits](https://developers.cloudflare.com/pages/platform/limits/)

### Inferences
- R2 is out: it needs a checkout and, per multiple reports, a payment method on file, and over-allowance usage bills instead of failing closed.
- A zero-cost mirror that does fit: split each model file into pieces under 25 MiB (for example 8 MB), publish them as static assets of a Cloudflare Pages project (free, no card, served from the LOS colo seen above), and have the loader fall back to Hugging Face Range requests if the mirror fails. 140 MB of whisper is about 18 pieces of 8 MB; the 2 GB Gemma file would be about 250 pieces, within the 20,000-file cap. The Render static site could host the same pieces (it is behind Cloudflare too) but Render counts them against monthly outbound bandwidth, so check Render's free bandwidth before doing that.
- Licences allow mirroring for whisper (MIT) and Gemma 4 E2B (Apache-2.0); Gemma 3 1B is under the Gemma Terms of Use, which permits redistribution with notice, but check the terms before mirroring.
- Measure before building: from this Mac, Cloudflare and HF throughput were similar (2.4 vs 1.2 to 2.2 MB/s); the gain from a Lagos mirror is mainly lower TTFB per piece and fewer hops, which helps flaky mobile links. A small A/B with real phones on MTN/Airtel would show whether it is worth it.

### Gaps
- No Cloudflare primary source states in so many words "R2 requires a payment method even on the free tier"; the conclusion rests on the official "checkout" wording plus third-party reports.
- Cloudflare Pages Free bandwidth limits and acceptable-use terms for serving large binary model files were not checked in this pass.
- Render free-plan outbound bandwidth allowance not checked.
